Fundraise Up API: what I noticed and where I'd start

Ekaterina Deys · prepared for the Senior Product Manager, API & Billing conversation · based only on public sources: the OpenAPI spec at api.fundraiseup.com/v1/openapi.json, the Webhooks docs, the REST API page and the job posting

How I read the role

API donation volume grew about 5× in a year and hundreds of integrations depend on it, but the posting calls the API an under-built area. The job is to turn a set of endpoints that work into a platform partners can build businesses on: faster first integration, safe writes at volume, self-serve partner onboarding. The "Billing" part is donor payments: local methods, recurring retries, payment infrastructure. That's the part I've spent the last four years on.

What's already good

  • Webhooks are well designed: HMAC-signed with secret rotation, at-least-once delivery with stable event ids, exponential retries for about 8 hours, a delivery log, manual resend, test events.
  • Fundamentals are right: cursor pagination where pages never silently skip records, a Request-Id on every response, granular per-resource keys for live and test data, deprecations announced with a date.
  • The API ships steadily: BACS, PAD and ACH, fee calculation and supporter-covered fees, upgrade links, and designation batch endpoints, all in 2026.

Billing side: where my experience maps directly

Recurring payment retries. At inDrive I designed failover based on soft and hard decline classification: retry only what can succeed, on the right schedule or a different route, and never retry a hard decline. For recurring giving that means smart retries by decline reason, card updater, and nudging donors to update the card through the existing Donor Portal links before the plan lapses. KPI: recovered recurring revenue and involuntary churn.

Local payment methods. I took payment orchestration from 4 to 40+ countries with 2–3 providers per country. Choosing which method to add next is a sizing exercise: donation volume by country × method share × expected conversion lift, against integration cost.

Payment infrastructure. One internal state model for every provider's statuses, health monitoring with automatic exclusion and gradual return (96.4% provider SLA), cost-aware routing (~$100K/month saved). That's directly useful as Fundraise Up adds methods beyond Stripe.

Partner integrations. At SkyRo I standardized integration contracts with PSPs and banks (schemas, ids, status transitions, error mapping), and a new partner went from unpredictable to a steady 2.5 weeks. That's the same muscle as cutting time to first successful call.

Questions I'd like to ask

  • Where do integrations stall today: Stripe setup, permissions, limits, docs? Is the key-to-first-live-donation funnel measured?
  • How much of "billing" is payment-method expansion versus recurring retries and recovery this year?
  • How does the API team work with GTM and the Customer Advisory Board? Who decides between a partner's ask and the platform roadmap?
