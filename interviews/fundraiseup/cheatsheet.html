3. Техника · принцип → мой опыт → «у вас я заметила»

IdempotencyRU: Idempotency-Key в заголовке, сервер хранит ключ и результат ~24ч, повтор возвращает тот же ответ; тот же ключ + другое тело → 422/409; ключ в рамках аккаунта. В inDrive повтор на PSP B шёл в той же транзакции. У вас: в POST /v1/donations ключа нет, а F2F-партнёры на плохой сети.
EN: The client sends an Idempotency-Key; the server stores the key and the response for ~24h and returns the same result on a retry. Same key with a different body is an error. Your donations POST doesn't have one yet, and F2F partners retry on bad networks.
WebhooksRU: at-least-once + стабильный event.id для дедупликации, HMAC-подпись с меткой времени и ротацией секрета, экспоненциальные ретраи на 5xx/таймаут, лог и повторная отправка, порядок не гарантирован. Получателю: быстро ответить 200, обрабатывать асинхронно. У вас: всё это есть; следующий шаг — управление вебхуками через API для партнёров.
EN: At-least-once delivery with a stable event id, HMAC signatures with rotation, exponential retries, a delivery log and resend; ordering isn't guaranteed. Yours already do this; next is a webhook management API for partners.
VersioningRU: не ломает: новые эндпоинты и необязательные поля. Ломает: удаление/переименование полей, смена типа, новый обязательный параметр. Подходы: /v2 или версия по дате в заголовке (как у Stripe). Депрекация: дата, гайд, Sunset-заголовки, мониторинг, кто на старом. У вас: хорошая практика с депрекацией полей events к 30.10.
EN: Additive changes are safe; removing or renaming fields, changing types or adding required params break clients. URL versions or date-based versions per account; deprecate with a date, a guide and monitoring.
Keys vs OAuthRU: API-ключ — своя интеграция организации; OAuth (authorization code + scopes) — партнёрские приложения на много клиентов, клиент сам подключает и отзывает. Ключи: least privilege, live/test, префиксы, хэш, ротация, аудит. У вас: для Partner API Program нужен OAuth «connect».
EN: API keys for an org's own integration; OAuth with scopes for partner apps serving many clients. Least privilege, live/test separation, prefixes, rotation, audit.
Limits & bulkRU: concurrency vs rate (token bucket), на ключ/аккаунт/партнёра, тиры; 429 + Retry-After. Массово — асинхронный batch с job id и результатом по каждому элементу. У вас: 3 параллельных запроса и по одному пожертвованию; для designations batch уже есть — логику можно перенести.
EN: Concurrency or rate limits per key, account or partner app; 429 with Retry-After; async batch jobs with per-item results for imports.
Метрики APIRU/EN: время до первого успешного вызова · воронка ключ → тестовый вызов → живое пожертвование · активные интеграции · объём через API · доставка вебхуков · 4xx по типам (где непонятны доки) · тикеты на интеграцию · разговоры с топ-партнёрами (CAB).
Billing (доноры)RU: ретраи регулярных платежей по причине отказа (soft — повторить по расписанию, hard — нет), card updater, напомнить донору обновить карту до сбоя. Новые методы оплаты — по формуле объём × доля метода × прирост конверсии против стоимости интеграции.
EN: Smart retries by decline reason, card updater, nudge donors before the plan lapses; size new payment methods by volume × method share × conversion lift vs integration cost.
